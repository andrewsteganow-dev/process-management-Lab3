на примере кода как ответить Вопрос: объясните, что будет если попытаться смонтировать /proc без изоляции mount-пространства.

Чтобы ответить на этот вопрос на примере вашего кода на C++, достаточно рассмотреть изменение флагов в системном вызове clone() в функции main():
cpp
// Убираем флаг изоляции mount-пространства (CLONE_NEWNS)
int flags = CLONE_NEWPID | /* CLONE_NEWNS | */ CLONE_NEWUSER |
            CLONE_NEWUTS | CLONE_NEWIPC | CLONE_NEWNET | SIGCHLD;

pid_t child_pid = ::clone(child_fn, stack_top, flags, &args);

Если убрать флаг CLONE_NEWNS, дочерний процесс останется в общем пространстве монтирования хоста, хотя и получит новое пространство процессов (CLONE_NEWPID). Дальнейшее поведение программы зависит от прав запуска.

1. Запуск от обычного пользователя (rootless-режим)

При запуске ./runtime run --rootfs /tmp/alpine /bin/ps без sudo программа аварийно завершится с ошибкой EPERM (Operation not permitted) еще до монтирования /proc:
• Где сломается код: Выполнение прервется на первой е операции изменения таблицы монтирования в child_fn:cpp
check_syscall(::mount(nullptr, "/", nullptr, MS_REC | MS_PRIVATE, nullptr), "mount MS_PRIVATE");
// Выбросит исключение: std::system_error -> mount MS_PRIVATE: Operation not permitted


(Даже если удалить эту строку и pivot_root, вызов ::mount("proc", "/proc", "proc", 0, nullptr) вернет ту же ошибку EPERM).
• Причина на уровне ядра: Флаг CLONE_NEWUSER наделяет процесс привилегией CAP_SYS_ADMIN только внутри его пространств имен. Поскольку CLONE_NEWNS не указан, таблица монтирования принадлежит родительскому user namespace хоста, которым владеет реальный системный root. Ядро блокирует попытку непривилегированного процесса менять точки монтирования основной ОС.

2. Запуск с реальными правами root (через sudo)

Если запустить программу от настоящего суперпользователя (sudo ./runtime ...) без флага CLONE_NEWNS (или с флагом CLONE_NEWNS, но без перевода корня в режим MS_PRIVATE):
• Что произойдет с системой: Вызов ::mount("proc", "/proc", "proc", 0, nullptr) успешно выполнится, но смонтирует новую файловую систему procfs поверх системного каталога /proc всей хостовой машины.
• Последствия для хоста:
	• Таблица процессов в /proc на хосте перезапишется процессами из нового PID namespace (где виден только один процесс с PID 1).
	• Системные утилиты и службы на хосте (ps, top, htop, systemd, демоны мониторинга) перестанут видеть реальные процессы операционной системы.
	• После завершения контейнера в корневом /proc хоста останется «сломанная» или пустая точка монтирования, из-за чего стандартные команды на хосте начнут выдавать ошибки (например, Error: /proc must be mounted), пока /proc не будет перемонтирован вручную (mount -t proc proc /proc).

5. Ответ на контрольный вопрос

Вопрос: Объясните, что будет, если попытаться смонтировать /proc без изоляции mount-пространства.

Ответ:
Если при создании процесса в clone() не указать флаг CLONE_NEWNS, дочерний процесс останется в общем пространстве монтирования хоста, несмотря на наличие изолированного PID namespace. Дальнейшее поведение зависит от прав запуска:
1. При запуске в rootless-режиме (от обычного пользователя с CLONE_NEWUSER, но без CLONE_NEWNS):
Попытка изменить таблицу монтирования (вызов mount(..., MS_PRIVATE) или mount("proc", "/proc", ...)) завершится ошибкой EPERM (Operation not permitted). Привилегия CAP_SYS_ADMIN, полученная внутри нового user namespace, действует только на ресурсы, принадлежащие этому пространству имен. Поскольку таблица монтирования принадлежит родительскому пространству имен хоста (владелец — реальный root), ядро Linux блокирует любые попытки непривилегированного пользователя изменить точки монтирования основной ОС.
2. При запуске от имени реального root на хосте (без CLONE_NEWNS или без флага MS_PRIVATE):
Системный вызов mount("proc", "/proc", "proc", 0, nullptr) выполнится успешно, но перезапишет системный каталог /proc всей хостовой системы таблицей процессов изолированного контейнера.
	
• Последствия для хоста: Системные утилиты и службы на хосте (ps, top, systemd, демоны мониторинга)
потеряют видимость реальных процессов операционной системы и будут видеть только процессы контейнера (начиная с PID 1).
 
После завершения контейнера в /proc хоста останется невалидная точка монтирования, что нарушит работу системных утилит до ручного перемонтирования /proc.
